# Leonida (Rust): roadmap for every phase

**Spec:** `docs/specs/2026-11-26-leonida-rust-design.md`

This roadmap fixes the order, scope, interfaces and exit criteria of every milestone, from the empty repository to
booting the game. It is not itself a step-by-step plan. Each milestone gets its own test-first plan, with complete
code like `2026-11-26-phase0-and-shader-container.md`, written when the milestone starts. Later milestones depend on
what earlier ones measure (how the corpus decodes, whether shaders carry reflection data, what the executable
imports), so writing their code now would be guessing.

## Rules for every milestone

- **Pure Rust** (spec section 2.1): no C or C++ in our code or in any dependency's build. Before adding a dependency,
  check that it builds without a C/C++ compiler.
- **No game data** in the repository. Tests build their inputs in code; checks against the real package run locally
  and only counts leave the machine.
- **Test first.** Every milestone plan follows the Phase 0 plan's pattern: failing test, minimal code, passing test,
  `cargo fmt`, `clippy -D warnings`, commit.
- **Exit criteria are measured, not claimed.** A milestone is done when its exit checks pass on the developer's
  machine (and in CI where they do not need game files or a GPU).
- **Fix, don't skip.** A shader, asset or call the code can't handle gets a rule, or a typed error and a count. It is
  never silently skipped.

## Order at a glance

```
M0 ─► M1.1 ─► M1.2 ─► M1.3 ─► M1.4 ─► M1.5 ─► M1.6 ─► M1.7 ─► M1.8 ──────────────┐
 │                       │                                                         ▼
 ├─► M2.1 ─► M2.2 ─┬─► M2.3 ─┬─► M2.6 ─► M2.7                    M3.3 ─► M3.4 ─► M3.5 ─► M3.6
 │                 ├─► M2.4  │    ▲                                ▲
 │                 └─► M2.5 ─┘    │                                │
 │                       └─► M3.1 ─► M3.2 ─────────────────────────┘
 │                                    │
 └─► M4.0 ─► M4.1 ─► M4.2 ─► M4.3 ─► M4.4    M4.5 (needs M3.2, M2.6) ─► M4.6 ─► M4.7 ─► M5 (needs the executable)
```

- **One developer, in order:** M0 → M1.1–M1.8 → M2.1–M2.6 → M3.1–M3.5 → M4.0–M4.7 → M5. M2.7 and M3.6 are
  optional.
- **With parallel workers:** Phase 2 and M4.0–M4.4 depend only on M0, so they can run alongside Phase 1. M3.1 can
  start once M1.3 has the minimal `gpu` crate.

## Size

| Phase | Milestones | Estimated Rust (code, excluding tests) |
|---|---|---|
| 0 | M0 | 2–4k |
| 1 Translator | M1.1–M1.8 | 60–80k |
| 2 Assets, systems, VFS | M2.1–M2.7 | 24–40k |
| 3 Renderer | M3.1–M3.6 | 25–38k |
| 4 Runtime | M4.0–M4.7 | 55–75k |
| 5 Boot | M5.1–M5.3 | unknown until the executable is measured |

Phase 1 is larger than the spec's first estimate because pure Rust adds our own SPIR-V assembler/disassembler and
validator (M1.6) and the RDNA2 assembler used by tests (M1.2).

## Phase 1: shader translator

### M1.1 — Shader containers

- **Plan:** `2026-11-26-phase0-and-shader-container.md`, Tasks 8–12 (written).
- **Delivers:** `shader-container` (carving, DXBC parts, XDAT/XBCH → FSSM, FSSM header and code range),
  `leonida shaders scan`.
- **Exit:** the scan of the real `shaders.rpf` reports 26,503 containers, 23,841 wave64 / 2,662 wave32, 195 with two
  payloads, no problems. The `container parts` line answers whether reflection data exists.

### M1.2 — `rdna`: instruction tables, decoder, assembler

- **Depends on:** M1.1 (code ranges to decode).
- **Delivers:**
  - `rdna` crate: one instruction table drives the decoder, assembler and printer.
  - Typed `Inst { op, operands, modifiers, encoding, address }`. Operands cover scalar and vector register ranges,
    special registers (VCC, EXEC, M0, SCC, ...), inline constants, 32-bit literals and `op_sel`/neg/abs/clamp/omod
    modifiers.
  - Every encoding family RDNA2 (gfx10.3, `gfx1013`) uses: SOP1, SOP2, SOPK, SOPC, SOPP, SMEM, VOP1, VOP2, VOPC,
    VOP3, VOP3P, DPP8, DPP16, SDWA, DS, MUBUF, MTBUF, MIMG (including NSA), EXP, FLAT, GLOBAL, SCRATCH.
  - `leonida shaders disasm <hash>`.
- **Table source:** a Rust port of upstream's `tools/rdna2_isa_tables.py` and `tools/rdna2_decode.py`. Both are
  GPL-3.0 like this project, so porting them is clean. AMD's machine-readable RDNA2 ISA and `llvm-mc` serve as
  development cross-checks only.
- **Tests:**
  - Golden decode and encode tests per encoding family.
  - `proptest` round trips: decode(encode(i)) == i, and encode(decode(w)) == w for valid words.
  - `cargo xtask rdna-crosscheck`: compares our printer against `llvm-mc --disassemble -mcpu=gfx1013`, on random
    words and on the local corpus. Development only.
- **Exit:**
  - Every instruction in all 26,503 code ranges decodes, with zero unknown opcodes.
  - The corpus cross-check against `llvm-mc` shows no differences.
- **Size:** 6–9k.

### M1.3 — `gpu` (minimal) and `testkit`

- **Depends on:** M1.2.
- **Delivers:**
  - **`gpu` (minimal):** Vulkan 1.3 instance and device selection through `ash`; buffers; compute pipelines from
    SPIR-V; dispatch and readback; subgroup size and supported operations. Validation layers can be switched on
    through an environment variable.
  - **`testkit` CPU reference:** an RDNA2 interpreter for wave32 and wave64. It covers:
    - scalar and vector ALU: f32, f16, i32, i16, packed math, conversions;
    - compares, VCC, EXEC and SCC;
    - lane operations: readlane, writelane, permlane, DPP, `ds_swizzle`, `ds_permute`, `ds_bpermute`;
    - LDS, buffer loads and stores, branches.

    Its float behaviour (denormals, NaN, rounding, output modifiers) follows the hardware facts upstream measured.
  - **Differential harness:** runs the same program and inputs on the CPU interpreter and as SPIR-V on the GPU, then
    compares lane by lane. In this milestone it is exercised with WGSL kernels compiled by `naga`; translated shaders
    plug in at M1.6.
  - **Ported expectations:** values upstream measured on real AMD and NVIDIA hardware (its `tests/semantic/*_hw.py`
    and fixtures), extracted into data files under `crates/testkit/expectations/`.
- **Exit:**
  - The interpreter matches every ported expectation.
  - The harness runs a `naga`-compiled kernel on the NVIDIA GPU and compares its results.
- **Size:** 10–15k.

### M1.4 — `shader-ir`: IR, lifting, SSA

- **Depends on:** M1.2, M1.3.
- **Delivers:**
  - **IR:** arena-based. Typed values (i1, i16, i32, i64, f16, f32, f64, vectors). Wave operations and EXEC are
    explicit. Memory and image operations carry their descriptor source.
  - **Lifting:** RDNA2 instructions become IR. The control-flow graph comes from `s_branch`, `s_cbranch_*` and
    `s_endpgm`. Indirect jumps (`s_setpc`, `s_swappc`) are lifted where their targets are provable, and are otherwise
    a typed error with a count.
  - **SSA construction** (Braun et al.).
  - **IR tools:** an IR interpreter, a printer and a verifier.
- **Tests:**
  - Differential: thousands of random RDNA2 programs, run by the `testkit` interpreter and by the IR interpreter on
    the lifted IR, with identical results required. No GPU needed.
  - Hand-written fixtures for each lifting rule.
- **Exit:** every corpus shader lifts to verified SSA IR; the random differential tests pass.
- **Size:** 10–14k.

### M1.5 — Control flow: divergence recovery and structurizer

- **Depends on:** M1.4.
- **Delivers:**
  - **Divergence recovery:** recognises the compiler's exec-mask idioms (`s_and_saveexec`, `s_andn2`/`s_or` on EXEC,
    `s_cbranch_execz`/`execnz`) and turns them into per-lane if/else and loops.
  - **Structurizer:** regions with SPIR-V merge and continue information; node splitting for irreducible graphs; a
    dispatch-loop fallback.
- **Tests:**
  - IR-interpreter equivalence before and after each pass, on hand-written graphs (irreducible, nested loops,
    early exits) and on random programs.
  - Corpus counts of shaders that need node splitting or the fallback.
- **Exit:** every corpus shader is structurized; the equivalence tests pass; the fallback count is reported.
- **Size:** 5–8k.

### M1.6 — SPIR-V emission, `spirv-text`, validation

- **Depends on:** M1.5.
- **Delivers:**
  - **Emission:** binary SPIR-V through `rspirv`.
    - **Entry points** for vertex, pixel, compute, mesh and geometry shaders.
    - **Interfaces** from the FSSM tables (pixel inputs at 0x138, exports, binding table after the code).
    - **Descriptor model:** the shader's own RDNA2 descriptors (T#, V#, S#) are read from the bindless heap; buffer
      device addresses; user SGPRs as push constants.
    - **Instruction coverage:** all ALU and conversions; image sample, load, store and gather; buffer operations and
      atomics; LDS as workgroup memory; exports; subgroup operations; barycentrics; `image_bvh_intersect_ray` (the
      shader walks the BVH itself, as in upstream).
  - **`ShaderInterface`:** a typed description of everything the renderer must bind.
  - **Validator:** our own checks of ID definitions and uses, types, structured control flow, decorations and
    capabilities.
  - **`spirv-text` crate:** SPIR-V assembler and disassembler built from the SPIR-V grammar tables. The `.spvasm`
    overrides and exports depend on it.
- **Tests:**
  - GPU differential tests are now live: compute snippets go through the full pipeline (RDNA2 → IR → SPIR-V → GPU)
    and are compared with `testkit`.
  - Vertex and pixel stage tests render small triangles and read the results back.
  - Upstream's ~6,000 translator test cases (inputs and expected values) ported as data-driven cases.
  - `spirv-text` round trips: binary → text → binary must give identical bytes.
  - CI runs `spirv-val` over our test outputs as an independent cross-check.
- **Exit:**
  - All wave32 corpus shaders and all wave64 compute and mesh shaders translate and pass our validator, and
    `spirv-val` on the development machine.
  - The differential suite passes on the NVIDIA GPU.
- **Size:** 22–30k.

### M1.7 — Wave64 lowering

- **Depends on:** M1.6.
- **Delivers:**
  - **Compute and mesh:** exact emulation. Each 64-lane wave runs as two 32-lane subgroups; ballots, readlanes,
    permutes, DPP and reductions go through workgroup memory with barrier rounds; masks are 64-bit.
  - **Vertex, pixel and geometry:** a cross-half analysis and an exactness label per shader.
  - **Target choice:** the build asks the `gpu` crate for the subgroup size. On 64-wide AMD GPUs it uses native
    wave64 (via subgroup size control); otherwise, emulation. The choice is recorded with each shader.
- **Tests:** wave64 differential cases on the NVIDIA GPU against the wave64 CPU interpreter, plus a per-operation
  cross-half analysis suite.
- **Exit:** all 26,503 shaders translate and validate, an exactness report exists, and the wave64 differential suite
  passes on NVIDIA.
- **Size:** 5–8k.

### M1.8 — `shader-store` and the shader commands

- **Depends on:** M1.7.
- **Delivers:**
  - The `redb` store (spec 4.4), filled by parallel translation (`rayon`) in batched transactions. Rebuilds are
    incremental by translator version.
  - **Commands:** `leonida shaders build | report | text <hash> | edit <hash> | export | check`.
  - **Overrides** read through an `OverrideSource` trait. A plain folder reader covers it until `vfs` (M2.6) provides
    the real one.
- **Exit:**
  - Spec 4.5 is met: the full corpus translates, validates and is labelled.
  - The test suite passes.
  - Full-corpus translation time is recorded as the baseline.
- **Size:** 3–5k.

## Phase 2: assets, systems, virtual file system

Phase 2 depends only on M0, so it can run alongside Phase 1. The formats come from upstream's `docs/`, which is in
the zip; its archive decoder submodule is not.

### M2.1 — `rpf9`: archive scanning and asset index

- **Delivers:**
  - Scanning for plaintext resources (resource headers as measured in upstream `docs/design.md` and the format
    notes), validating each one, and indexing it in `redb`: archive, offset, size, type, name hash, content hash.
  - Indexing of texture pools (`.ttpf`).
  - Name recovery: hash dictionaries built from names found in the game's own data (Jenkins one-at-a-time hashes).
  - `leonida assets index`, `leonida assets list <filter>`.
- **Exit:**
  - Every archive and pool is indexed.
  - Counts match upstream's recount, e.g. 382,781 models, 343,327 of them from `levels.rpf`.
- **Size:** 4–6k.

### M2.2 — Textures

- **Delivers:**
  - **BCPack decoder:** the rANS entropy decoder back to BC1, BC3, BC4, BC5, plus BC6H and BC7 wherever their
    history is known. Ported from upstream's `tools/bcpack.py` and its vendored Rust `bcpack-rs`, after checking that
    crate's license.
  - **Detiling** of the console's GFX10 memory layout: a CPU reference version, and a WGSL compute version compiled
    by `naga`.
  - DDS export, with optional PNG previews.
- **Exit:** DDS files open in Paint.NET; GPU and CPU detiling match bit for bit; textures with unknown history are
  counted and use placeholders.
- **Size:** 4–7k.

### M2.3 — Models and materials

- **Delivers:**
  - Readers for drawables, vertex declarations, index buffers, LODs, skeletons, skinning and materials (shader
    hashes, texture links, parameters).
  - glTF export through `gltf-json`, with a `.json` sidecar per model. Mesh compression only if a pure-Rust
    meshopt encoder is available (the common `meshopt` crate wraps C++).
- **Exit:** a character exports with its skeleton and opens correctly in Blender; model counts match the index.
- **Size:** 5–8k.

### M2.4 — Audio

- **Delivers:**
  - Reading AWC banks.
  - Opus streams repackaged losslessly as Ogg Opus.
  - PCM as WAV.
  - **Our own XMA2 decoder.** XMA2 is built on WMA Pro. Reference sources are the public format descriptions and
    ffmpeg's LGPL decoder (LGPL code may be ported into a GPL-3.0 project). Check upstream's
    `runtime/xma_decoder` first.
- **Exit:**
  - Every bank exports.
  - XMA2 output matches ffmpeg's within tolerance; this is a development check.
- **Size:** 4–7k.

### M2.5 — `systems`

- **Delivers:**
  - Binary XML (RBF0) ↔ XML in both directions.
  - Text tables → JSON; mission tables; timecycle.
  - The other systems upstream measured, laid out as the `Systems/` tree.
  - Notes in place of systems whose formats aren't decoded yet.
- **Exit:** every measured system round-trips: binary → XML → binary gives identical bytes.
- **Size:** 3–5k.

### M2.6 — `vfs`, packages, mods, export tree, `Config/`

- **Delivers:**
  - The layered virtual tree (base game → Leonida fixes → `Mods/`).
  - Package manifests, with dependency and version checks.
  - `Config/mods.toml` load order.
  - **Commands:** `leonida mods list | conflicts | enable | disable`, and `leonida assets export <path>` filling the
    X-Plane-style tree.
  - `Config/*.toml` reading.
  - A `vfs` implementation of M1.8's `OverrideSource`.
- **Exit:** conflicts are reported with their winners; a shader override in a package wins over the generated shader;
  exports open in their tools.
- **Size:** 3–5k.

### M2.7 — `leonida mount` (optional)

- **Delivers:** the virtual tree shown in Explorer through Windows Projected File System (`windows` crate). Files are
  decoded when first opened.
- **Size:** 1–2k.

## Phase 3: renderer

### M3.1 — `gpu` (full)

- **Depends on:** M1.3.
- **Delivers:**
  - Device setup with the required features (mesh shaders, fragment barycentrics, descriptor indexing, buffer device
    address, synchronization2).
  - The bindless descriptor heap model the translator emits (M1.6).
  - Memory through `gpu-allocator`.
  - A persistent pipeline cache.
  - A swapchain and window through `winit`.
- **Size:** 5–8k.

### M3.2 — `render` core

- **Depends on:** M3.1, M2.2.
- **Delivers:** asynchronous streaming and upload, GPU detiling during upload, the frame loop, and a debug overlay
  (`egui`, pure Rust).
- **Size:** 6–9k.

### M3.3 — `scene` harness

- **Depends on:** M3.2, M2.3, M1.8.
- **Delivers:**
  - Steps 1–4 of the spec (section 8): our own shader, then the game's vertex shader, then the game's vertex and pixel
    shaders with textures, then the game's deferred passes.
  - **Constant-buffer layouts:** read from reflection data if M1.1 found any. Otherwise a `leonida shaders cbuffers`
    tool infers each shader's layout from how it uses each offset.
- **Exit:** each step renders a recognisable game model, checked by eye and by a reference image of a synthetic
  scene.
- **Size:** 8–12k.

### M3.4 — `leonida pipelines`

- **Depends on:** M3.3.
- **Delivers:** every pipeline built ahead of time, the cache saved, and any skipped pipeline reported with its
  reason.
- **Exit:** the full corpus builds on the NVIDIA driver, with failures listed by cause.
- **Size:** 1–2k.

### M3.5 — Renderer upgrades

- **Depends on:** M3.3.
- **Delivers:** internal resolution scaling, FSR 1 ported to WGSL (MIT), and texture filtering overrides, all in
  `Config/graphics.toml`.
- **Size:** 2–4k.

### M3.6 — `leonida view` (optional)

- **Depends on:** M3.3, M2.6.
- **Delivers:** a native map and model viewer over the virtual tree, replacing upstream's web viewer.
- **Size:** 3–5k.

## Phase 4: runtime (Windows)

Phase 4 can only be tested on synthetic programs until a game executable is available. M4.0–M4.4 depend only on M0.

### M4.0 — Runtime groundwork

- **Delivers:**
  - **Toolchain decision for the runtime:** the current `x86_64-pc-windows-gnu`, or `x86_64-pc-windows-msvc` linked
    with `rust-lld`. Both stay free of C/C++. The decision rests on exception and unwinding interplay with the game's
    MSVC-built code, tested with a synthetic MSVC-ABI image.
  - **`shim-macros` proc-macro crate:** `#[shim("dll", "name")]` and compile-time registration of shims.
  - **`pe-builder` test crate:** writes small synthetic PE images (sections, imports, relocations, TLS, exception
    tables) for the loader tests.
- **Size:** 2–3k.

### M4.1 — `pe-loader`

- **Delivers:** the spec 9.1 steps in order:
  1. mapping and relocations;
  2. imports and delay imports;
  3. TLS, through a helper Rust `cdylib`;
  4. exception tables;
  5. write-then-execute page protections;
  6. jumping to the entry point.

  Also import-name validation, and patching through `iced-x86`.
- **Tests:** synthetic images from `pe-builder` (relocated, TLS callbacks, delay imports, C++-style exceptions
  thrown across our frames), plus property-based fuzzing of the header parsing with `proptest` (`cargo-fuzz` would
  compile C++ libFuzzer, so it is not used).
- **Size:** 3–5k.

### M4.2 — `shims` core

- **Delivers:**
  - Process, thread, synchronization, time, TLS and heap shims.
  - The file system on `vfs`.
  - `xmem`.
  - `LoadLibrary`/`GetProcAddress` with pseudo-handles.
  - bcrypt random numbers.
  - Basic COM.
  - **Offline policy:** host DLL allow-list, blocking stubs for network DLLs.
  - `leonida run --dry-run <image>`.
- **Exit:** `--dry-run` over the package's own DLLs lists every import as shimmed, host, blocked or missing; the
  synthetic programs run end to end.
- **Size:** 10–15k.

### M4.3 — GDK shims

- **Delivers:**
  - `xgameruntime`: core, user, store, saves (to `Output/saves`), offline answers.
  - A Rust reimplementation of `XTaskQueue`.
  - Telemetry dropped.
- **Size:** 8–12k.

### M4.4 — Input and audio runtime

- **Delivers:** a GameInput shim on `gilrs`, with DualSense extras over HID; XAudio2/XMA shims on `cpal` and the
  M2.4 XMA2 decoder.
- **Size:** 5–8k.

### M4.5 — `xbox-d3d12`

- **Depends on:** M3.2, M2.6, M1.8.
- **Delivers:**
  - The device and its slot table (`d3d12_slots.toml`).
  - Resources, heaps and descriptors.
  - Command-list recording and replay on Vulkan.
  - Pipeline state objects through the shader store.
  - Queries and fences.
  - PresentX to the swapchain.
  - Unknown slots trap with their slot number and caller.
- **Tests:** synthetic D3D12 call sequences, recorded as data and replayed against reference images.
- **Size:** 25–35k.

### M4.6 — Ray tracing

- **Depends on:** M4.5.
- **Delivers:**
  - BLAS and TLAS builds in the console's XDXR BVH4 layout (WGSL compute), as upstream documents in `docs/xdxr.md`
    and `docs/bvh.md`.
  - Refit, clone and compaction.
- **Tests:** checked against a CPU reference build on synthetic scenes.
- **Size:** 6–9k.

### M4.7 — First-boot kit

- **Delivers:**
  - `leonida run --trace`, which writes the `Output/boot/` reports (imports hit, unknown slots, files touched, last
    address).
  - Crash minidumps through `minidump-writer` (pure Rust).
- **Exit:** a synthetic program that calls an unknown D3D12 slot produces a report naming that slot and its caller.
- **Size:** 2–3k.

## Phase 5: boot (needs the game executable)

Phase 5 cannot start until a game executable from the developer's own copy is available.

### M5.1 — First contact

`leonida run --dry-run` on the executable. Every missing import becomes a task in its own plan.

### M5.2 — Boot loop

Repeat until the game presents its first frame of its own rendering, then its title screen:

1. run with `--trace`;
2. read `Output/boot/`;
3. fix the next blocker (a shim, a D3D12 slot, a translator rule);
4. add a regression test.

### M5.3 — Game-side hooks

Through `iced-x86` patches on measured functions:
- resource-level mod overrides through the virtual tree;
- uncapped frame rate;
- ultrawide.

## Risks to watch (beyond spec section 13)

1. **Our validator is less thorough than `spirv-val`.** Mitigation: the CI and development cross-check on every
   corpus run, and driver pipeline creation in M3.4.
2. **`naga` WGSL limits for our own shaders** (subgroups, 64-bit atomics in BVH builds). Mitigation: write the rare
   kernel that needs more directly as SPIR-V with `rspirv`'s builder (still pure Rust).
3. **XMA2 decoder effort** (M2.4): the largest single unknown in Phase 2. Until it lands, banks export undecoded and
   the runtime plays silence.
4. **License checks** for anything ported: upstream (GPL-3.0, fine), `bcpack-rs` (check), ffmpeg as XMA2 reference
   (LGPL, compatible). AMD's ISA XML is only used as a cross-check, never shipped.
5. **The runtime toolchain** (M4.0) could change how panics and C++ exceptions cross between our code and the
   game's. It is settled with a synthetic test before M4.1 builds on it.
